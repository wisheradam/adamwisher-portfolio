# Publication and public cutover

[Handbook](README.md) · [Module reference](modules.md) · [Operations](operations.md)

## Working content and published snapshots

[`005_publication_snapshots.sql`](../../lib/admin/migrations/005_publication_snapshots.sql)
and [`publication.ts`](../../lib/admin/publication.ts) cover six entity tables.
They are `experience`, `education_records`, `certifications`, `products`,
`releases` and `timeline_events`. A working row is editable in Admin. The public
reader uses the current JSON snapshot indexed by entity type and ID. Snapshots
include the publisher, timestamp and a current revision counter.

| Action | Working content | Public snapshot |
| --- | --- | --- |
| Create or save Draft | Persist validated changes | Keep any existing snapshot |
| Save Review, where supported | Mark working copy for editorial review | Keep any existing snapshot |
| Publish | Persist submitted data or the saved row selected by the row action | Insert or update the current snapshot and record a publication audit event |
| Archive / unpublish | Retain working row and mark archived | Remove snapshot |
| Delete | Soft-delete the working row | Remove snapshot in the same transaction |

Review is a working status. It has no approval queue or mandatory second approver.
Apps use product-specific working statuses and do not accept `REVIEW`. The
Admin list distinguishes Unpublished, Published, and Published with unpublished
changes by comparing working content against the snapshot. Row-level publication
actions use the saved record. Save an intended change before publishing it with
that action. A direct authorized publish request can promote the submitted data.

The write path validates values, locks the working row for update, updates the
snapshot where applicable and writes audit in one transaction. If the audit or
snapshot write fails the transaction rolls back. The Admin UI supplies the
previous `updated_at` for optimistic concurrency. Tokenless compatibility
requests are still accepted and do not get that stale-edit check. Migration 005
backfills then-current eligible legacy content and protects against resurrecting
already-unpublished rows on rerun. It cannot reconstruct an older approval.

## Public visibility

A current snapshot must be PUBLIC and non-deleted. Releases and Timeline also
require each linked parent to be eligible. App and release parents use public
snapshots. Legacy Project parents use the live published/public/non-deleted row.
Removing an eligible parent can hide descendants while preserving their working
rows and their own snapshots. Public readers are request-driven without a process
snapshot cache. Already-open pages need a refresh to see changes.

Legacy Projects use explicit status and visibility on the stored row. Their public
records are eligible for the Work catalog only when the database source is enabled.
The six static case studies keep their routes and content. Media file delivery on
`main` remains authenticated through Admin. The draft S3 public endpoint has its
own publication checks and release gates.

| Switch | Current behavior in source |
| --- | --- |
| `PUBLIC_CONTENT_SOURCE=database` | Enables database-backed Work additions, Apps content, History, feature-flag lookup and SEO overrides where wired. Absence preserves the existing static behavior. |
| `PUBLIC_KNOWLEDGE_CUTOVER_SHA` | Must match the hash of public source IDs generated by the knowledge reconciler. The factual reader uses static sources if it is missing or mismatched. With an exact match the public reader consumes approved snapshots. A configured DB failure is surfaced. |
| `PUBLIC_REDIRECTS_ENABLED=1` | Enables managed redirects only with the database source selection. |
| Runtime flags | Code defaults are Apps on, History off, Ask Adam on, Education on and Experimental Projects off. Verify the caller because a defined key can lack a runtime consumer. |

The knowledge gate is separate from the general source switch. Check both before
release, reconcile the import without overwriting Admin edits, and validate public
HTML, direct URLs, sitemap and metadata as well as the Admin preview.

## Rollback

Use explicit unpublish to remove one snapshot, or restore the intended working
content and republish after review. The current snapshot table is not a historical
revision store. Audit before/after payloads are evidence for a reviewed repair.
The UI does not offer one-click restoration of old revisions. Reverting application
code or cutover configuration also does not undo data or audit writes. Reconcile
the database and media independently using the [recovery guide](operations.md#backup-and-recovery).
