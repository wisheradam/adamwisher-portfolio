# Admin Console — Stage 1 data layer

The Admin Console is a draft at `/admin` on `feature/admin-console` (PR #8). **Do not merge or deploy yet.** Stage 1 replaces the filesystem SQLite runtime with PostgreSQL-compatible persistence. It does not provision or modify AWS resources. Stages 2 and 3 remain necessary before production: multi-user identity/RBAC and migration of the six source-controlled case studies.

## Database choice

Aurora PostgreSQL with RDS Data API is the target for preview and future production. The CMS has related Projects, Products and Audit Events, unique slugs, transactional writes, status constraints, and evolving queries. PostgreSQL keeps those rules in the database. Data API sends queries over the AWS SDK's HTTPS transport, so Amplify server instances do not maintain pools of PostgreSQL connections. IAM permissions and a Secrets Manager secret reference remain server-side. The repository already uses AWS SDK clients for Contact. This choice requires an Aurora PostgreSQL cluster with Data API enabled; none is created by this branch. A read-only inspection of the connected AWS account found the existing `adamwisher-site` Amplify `WEB_COMPUTE` app in `eu-north-1` and no RDS clusters in that region. Other regions and accounts were not inventoried. Aurora is a new managed resource and its cost, network placement, secret, backup settings, and IAM scope need a separate infrastructure review before preview or production deployment.

For local development and isolated integration tests, PGlite runs the same PostgreSQL schema from a durable, ignored local directory. It is **not** the production backend. No database is accessed at Next.js build time. Page and API queries run on the Node.js server. Migrations run only through `npm run admin:migrate`, never automatically during a request or build. Apply the migration separately in each environment before running the app. The SQL in `lib/admin/migrations/001_init.sql` is idempotent; the command records its version in `admin_schema_migrations`. Review new migration files before executing them. Run it once per environment through the deployment process with a single migration runner; do not run competing migration jobs.

## Environments and local setup

Run `npm ci`. Copy the variable **names** in `.env.example` into `.env.local` and supply a random 32+ character `ADMIN_SESSION_SECRET` and a unique scrypt `ADMIN_PASSWORD_HASH=scrypt:<salt>:<128-hex-character-hash>` (Node `crypto.scryptSync(password,salt,64).toString('hex')`). Never commit actual values. Set `ADMIN_DATABASE_DRIVER=pglite`, optionally `ADMIN_DB_PATH` (default `.data/admin-pg`). Run `npm run admin:migrate`, then `npm run dev`; open `http://localhost:3000/admin/login`. The old `.data/admin.sqlite` is retained locally but no longer read by the application. To preserve its records, after migrating run `npm run admin:import-sqlite -- .data/admin.sqlite`. This one-time, local-only import uses Python’s read-only SQLite access and inserts Projects, Products and Audit Events without overwriting destination IDs; rerunning it is safe. Back up both stores and compare counts before removing the old file. The import does not connect to Aurora.

For test, use a separate temporary `ADMIN_DB_PATH`, then migrate and run `npm run test:admin-data` after `npm run build`. The test creates its own database and credentials, exercises the real HTTP APIs, restarts the app, checks persistence and audit events, and deletes its temporary data.

For preview/staging and future production, set `ADMIN_DATABASE_DRIVER=aurora-data-api`, `ADMIN_DB_RESOURCE_ARN`, `ADMIN_DB_SECRET_ARN`, `ADMIN_DB_NAME`, and `AWS_REGION` as server-side runtime variables. These ARNs are references, not secret values. The runtime IAM principal requires only the necessary `rds-data:ExecuteStatement`, `rds-data:BeginTransaction`, `rds-data:CommitTransaction`, `rds-data:RollbackTransaction` for the intended cluster and `secretsmanager:GetSecretValue` for its secret. The separate migration runner also needs DDL permissions. Keep credentials and ARNs out of browser bundles. Configure the four environments with separate data and secrets; never point preview at production data. A preview infrastructure environment has not been created or tested here.

## Schema, lifecycle and recovery

`projects` and `products` have UUID text IDs, unique slugs, status and visibility checks, timestamps and soft deletion. `audit_events` has immutable event IDs, actor, action, entity reference, before/after state and timestamp. Changes and audit writes share a transaction. Indexes cover published listings, search-related listings and recent audit reads. No cascading foreign keys delete portfolio content; audit entity references remain after soft deletion. The single admin credential is still environment based: Stage 2 will add user records and server-enforced roles. Draft projects remain private; only `PUBLISHED` + `PUBLIC` records appear on public managed routes. Preview requires an admin session and is noindexed. Existing six static case studies remain source-controlled and keep their routes.

For Aurora, enable automated backups with retention appropriate to the site's recovery objective (proposed 7–14 days), deletion protection and a manual snapshot before schema changes. Record the snapshot identifier and migration version. To recover, restore to a **new** cluster, validate counts and sample records, point a nonproduction environment at the restored cluster, then perform a controlled configuration switch. Never assume a down migration can undo published content or audit writes. Roll back application code separately; forward-fix schema changes where data was written under a newer version. PGlite local backups are a copy of the stopped data directory.

## Remaining limitations

Stage 1 has not connected to a live Aurora cluster, verified actual Amplify IAM/Data API permissions, or tested backup restoration. Existing SQLite preview records require the explicit local import command; a live Aurora import has not been exercised. The Admin still has one SUPER_ADMIN credential without revocable sessions or login rate limiting. Other navigation modules are placeholders; existing case studies have not been migrated. No media upload, contact inbox, or Ask Adam management is included. Keep PR #8 in Draft until these stages and browser validation pass.
